# issue 29

## comment 2026-11-21 1

"[issue-1-1-3.md](./issue-1-1-3.md)" と "[issue-1-2-12.md](./issue-1-2-12.md)" において、 resolver のバージョンを LTS 23.28 に固定したけど、やっぱりライブラリとしての汎用性を求めるならば、複数の GHC に対応したい。

まず、実質的な LTS として GHC 9.6 がある。

GHC 9.6.7 に対応しているのは LTS 22.44 リソルバー（[リンク](https://www.stackage.org/lts-22.44)）である。

これについては、問題なく追加できる。

依存ライブラリのバージョンの制約を記述する時には "[issue-1-2-25.md](./issue-1-2-25.md)" において検討したように `network ^>= 2.6.3.6 || ^>= 2.7.0.2 || ^>= 2.8.0.0 || ^>= 3.0.1.0` という記法を用いる。

問題なのが GHC 9.10 で、 GHC 9.10.2 にはヤバいバグがいくつかあったはずだし、 GHC 9.10.3 は枯れたリソルバーがない、つまり、まだバージョンが更新されている状態なんだよね。

とりあえず GHC 9.10.2 の LTS 24.11 リソルバー（[リンク](https://www.stackage.org/lts-24.11)）を使うなら、新しいリソルバーが出ることはありえない。 LTS 24.12 リソルバーは GHC 9.10.3 のためのリソルバーになっているから、番号付けのルールとして GHC 9.10.2 の新しいリソルバーを出すことは不可能である。

GitHub Actions のキャッシュの問題についても、最も緩い `restore_keys` フィールドの指定でも `cache--stack-pantry--${{ env.CACHE_VERSION }}--${{ runner.os }}--${{ matrix.os.version }}--ghc-${{ matrix.haskell.ghc }}--` となっていて GHC 9.10.2 のジョブのキャッシュと GHC 9.10.3 のジョブのキャッシュが混ざる心配はいらない。

さっさと GHC 9.10 と GHC 9.12 に対応している最新のリソルバーを指定しておいて、なにか困ってからリソルバーを更新すればいいという考え方もある。 GHC 9.10.3 に対応している最新のリソルバーは LTS 24.67 リソルバー（[リンク](https://www.stackage.org/lts-24.67)）で、 GHC 9.12.4 に対応している最新のリソルバーは Stackage Nightly 2026-11-21 リソルバー（[リンク](https://www.stackage.org/nightly-2026-11-21)）である。

GHC のバージョンが上がる時には LTS 22.43 と LTS 23.0 の差分（[リンク](https://www.stackage.org/diff/lts-22.43/lts-23.0)）を見れば理解できるように、大規模な変更が入る。それだけではなく、パッチバージョンが上がるだけでも、カスケードして異なるビルド成果物がキャッシュされることになる。だからこそ、 GHC のバージョンを固定するならば枯れたリソルバーを使いたいのである。
